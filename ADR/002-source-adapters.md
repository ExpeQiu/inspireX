# ADR-002：三来源统一适配器，下游仍走同一入库管道

> 状态：已采纳  
> 日期：2026-08-19  
> 模板：1（采集→管道→展示）

## 背景

来源一（本地文件 / 外置卷 / 浏览器插件单张）已通。接下来要加：

- 来源二：订阅网页图片（用户举例 Pinterest）
- 来源三：对接生图 API（单张 / 批量）

三者最终都要进入同一素材库（去重 / 缩略图 / 主色 / CLIP）。

## 决策

| 项 | 选择 |
|----|------|
| 采集层 | **Source Adapter**：`local` / `web_feed` / `ai_gen` |
| 入库层 | **不新建第二条管道**；全部落到现有 `import_paths_with` / `import_from_url` |
| 出处 | `assets.source_kind` + `source_url` + 可选 `source_ref`（订阅 id / 生成 job id） |
| 来源二合规 | **RSS/Atom 公开源 + 公开 HTML 抽图（遵守 robots）+ 用户已打开页面的插件批量保存**；不做人机对抗式站点爬虫 |
| 来源三 | **类型 → 客户端 → 工厂 → 环境变量**；默认 `AI_MOCK_MODE=true` |
| 编排 | 沿用 `pipeline_runs`；订阅轮询与生图任务都记 `run_id` |

## 为何不用其他做法

- 不为 Pinterest 写独立爬虫仓：ToS 禁止无人值守抓取，且登录墙/动态加载不稳定。
- 不把生图做成常驻云服务：仍是个人全本地桌面；API 只在用户点「生成」或订阅 tick 时调用。
- 不引入模板 2/4：无场景合同 / Skill 中台需求。

## 后果

- 正：来源可插拔；入库、检索、拖出零改动。
- 负：Pinterest 类站点无法「登记 Board URL 就自动全量同步」；依赖 RSS、官方 API 或用户在页内批量保存。
